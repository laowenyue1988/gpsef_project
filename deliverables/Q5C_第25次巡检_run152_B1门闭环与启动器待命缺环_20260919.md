## §3 ★★本轮唯一实质发现（E-1）：启动器「待命余量」缺环

### 3.1 现象

`_q5c_launch.log` 尾部：

```
[2026-09-19 06:34:42] 等待中：活跃臂=1 可用=12166MB 未启=-
[2026-09-19 07:04:42] 等待中：活跃臂=1 可用=11770MB 未启=-
[2026-09-19 07:09:42] 两臂全部落臂 ⇒ 进入判据阶段
[2026-09-19 07:09:42] 执行判据：--ref …S17b_SL060PT150… --B 5000 --blocks 21,63 --arm …
[2026-09-19 07:09:44] 判据完成 rc=0 ⇒ 结论见 _q5c_verdict.log
```

`07:09:44` 后**无新行**，但轮询循环 `while it < 400` **未退出**（`it` 远未达 400）。

### 3.2 根因（读码确证，`_q5c_launch.py`）

| 位置 | 逻辑 | 后果 |
|---|---|---|
| `START_CHECK_MAX = 1`，主循环外**一次性**校验 | `if len(act0) > START_CHECK_MAX: return 3` | 该值**不随批次落臂重置** |
| 主循环 `if all(done(...)): break` 后进入判据段，**判据段之后无 `return`**（仅 `sys.exit(main())`） | 判据完成后代码**回落到主循环**，`launched` 已清空 | 每次轮询落入 `elif it % 6 == 1: log('等待中：活跃臂=0 …')` |
| `active_arms()` 按 `ACTIVE_AGE_S=300` 判「running」 | 未启臂时 `pend` 为空 `[]` | `elif pend:` **恒假** ⇒ **永不重复起臂** ✅ |

**⇒ 定性**：这是**fail-safe 设计**（不会重复起臂，**安全**）＋ **但是一次性的启动前校验**（不会接棒下一批次，**僵死**）。

### 3.3 为什么这是**实质发现**而非运维噪声

Q5N-a 的起臂前置是「`_q5n_launch.py` ＋ `_make_q5n_configs.py` ＋ `config_exp_Q5N_*.yaml`」**三件**。
本轮确认：**三件仍全缺**，且 `labels.py` 未改。单看这三件，会得出「主会话尚未开工」的判断。

**但 E-1 揭示**：即便主会话已完成七闸门改造、写出 YAML 与配置生成器，**若沿用 `_q5c_launch.py` 模式**，
仍会因 `START_CHECK_MAX=1`（`07:09` 时 `act0=0` **恰好 PASS**，但落臂后该值**不再有纠正机会**）而**无法接棒** ——
更关键的是：**当前没有任何进程对新 Q5N 批次待命**（`_q5c_launch` 只认 `ARMS` 常量中的 Q5C 两臂）。

> **⇒ 结论**：Q5N 的**真实阻塞点**不是「代码写得慢」，而是「**不存在为新批次待命的执行者**」。
> **新批次必须由新的 `_q5n_launch.py` 承担**（本自动化**无权创建**——只读权限，见 §0）。
