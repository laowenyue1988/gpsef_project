## 二、★本轮核心发现：E3 事件"停更"是误判 —— 澄清与证据

### 2.1 现象

初次扫描发现：`[E3-敞口] ... trend` 事件最后一跳为 **2023-08-02**，而逐日持仓日志已推进至 **2023-10-23**（含 **52 个交易日**）；**该区间 E3 事件数 = 0**。表观上像"敞口层停止工作"。

### 2.2 根因（源码证据）

`strategies/small_alpha191_test3/strategy.py` 第 4397~4415 行：

```python
_signal_type = str(gc.get('signal_type', 'vol')).strip().lower()
if _signal_type == 'trend':
    ...
    new_scale = 1.0 if _px_last > _ma_v else _floor
    prev = float(getattr(self, '_daily_vol_scale', 1.0))
    self._daily_vol_scale = new_scale
    if abs(new_scale - prev) > 1e-3:          # ← 关键：仅在 scale 发生变化时打印
        logger.info(f'[E3-敞口] {current_date.date()} trend ma{_ma_days}=...')
    return
```

⇒ **日志是"状态翻转事件"，不是"逐日快照"**。`scale` 未翻转时不打印。
2023-08-02 之后指数持续处于 `px ≤ MA60` 状态（`scale = 0.30` 保持），**故无新事件** —— 这是**设计如此**，非缺陷。

### 2.3 完整验证（4 项独立校验，全部通过）

| # | 校验项 | 结果 |
|---|---|---|
| 1 | **状态机严格交替** | 37 个事件中，相邻事件 `scale` **全部严格交替**（1.0 ↔ floor），**0 处同值重复** ⇒ 与 `abs(new-prev)>1e-3` 打印条件完全吻合 |
| 2 | **scale 分布** | `{0.30: 19, 1.00: 18}` ⇒ 共 37 次翻转，19 次降、18 次升，对称合理 |
| 3 | **逻辑自洽（逐条）** | 按 `px > MA60 → scale=1.0` / `px ≤ MA60 → scale=floor` 逐条核验：**T1 违反 0 / T2 违反 0**（`ma` 窗全部 = 60）|
| 4 | **唯一变量隔离（最强证据）** | T1 与 T2 的 `ma60` / `px` 字段 **逐位相同**（bitwise identical）、日期完全对齐；**仅 `floor` 不同**（0.30 vs 0.50）⇒ 证明两臂共享同一信号源、差异**纯由 floor 引起** |

> **更正记录（本轮自检）**：首次校验脚本报 `logic violations T1: 19`。经复核，系**我方校验脚本缺陷**（只检查了 `px ≤ ma` 分支，漏加 `ma_w == '60'` 条件，把 `ma20` 臂的残留条目误判为违规）。修正口径后 **违反 = 0**。此为**我方工具缺陷，非臂缺陷**，特此记录以免误导。

## 六、⑤小白版四问（D-269 强制）

### 这段在解决什么问题？

我们正在验证一件事：**当大盘（这里用中证 1000 指数的代理 `sh932000`）跌到 60 日均线以下时，就把股票仓位砍到三成（或五成）——这么做到底能不能让策略更稳、赚得更多？**

之前试过另一种做法：**看波动率**（波动大了就减仓）。结果很差（Q5D 已关闭那条路）：因为微盘股是"波动越大、后面涨得越多"，看波动率减仓等于**每次都在反弹前卖掉**。所以这轮换思路：**不看波动率，看趋势（均线）**。

### 用了什么办法？

两个实验臂（同一天起跑，只差一个数字）：

| 臂 | `trend_ma_days`（均线长度）| `trend_floor`（跌破均线时砍到几成）|
|---|---|---|
| **T1** | 60 天 | **0.30**（砍到三成）|
| **T2** | 60 天 | **0.50**（砍到五成）|

**开关名解释**：
- `signal_type = trend` —— 把敞口信号源从"波动率"切换成"趋势/均线"。
- `trend_ma_days = 60` —— 用过去 60 个交易日的收盘价平均值当"水位线"。
- `trend_floor = 0.3 / 0.5` —— 价格**跌破**水位线时，仓位缩放系数取这个值（即只留三成/五成）；价格**站上**水位线时，系数回 `1.0`（满仓）。
- 参数在配置文件 `garch_control` 段；两臂配置**仅 `trend_floor` 一处不同**（已逐字节核验）。

### 结果是什么？

**目前跑到一半，还不能下结论**，但运行质量已有硬证据：

1. **进度 47.1%**（620/1315 个交易日，已跑完 2021-04 至 2023-10-23），预计**今晚约 19:26 跑完**。
2. **降敞口时长 43.1%**（620 个交易日里有 **267 天**处于"砍仓"状态）—— 预注册的"有效性门槛"是 **>20%**，**43.1% 远超**。所以这条机制**确实在干活**，不是空跑。
3. **信号源干净**：两臂用的是**同一份**均线数据（`ma60` 与 `px` 数值逐位相同），差别**只来自 `floor` 那个数字** —— 这样最终结果差异才能**归因到 floor**，不会混淆。
4. **零故障**：`ERROR`、缺列、训练失败、`index out of bounds`、连续空仓 —— **全部 0 次**。
5. **本轮澄清了一个假警报**：我一开始发现"8 月 2 日之后敞口日志不再打印了（52 天没动静）"，看着像机制坏了。查源码发现：**日志只在"状态翻转"时打印**（从砍仓变满仓，或反过来）。8 月 2 日之后指数一直没爬回均线上方，所以状态**一直是砍仓**，**当然不会打印新日志** —— 这是**设计如此**，不是故障。这个澄清很重要，否则会误判成"敞口层停止工作"。
