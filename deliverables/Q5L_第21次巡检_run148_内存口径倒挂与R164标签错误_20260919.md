## 二、★★ 本轮核心发现：R-164 —— 启动器 CRITICAL 日志的「提交可用」标签错误（语义倒挂）

### 现象（表面冲突）

启动器日志每几分钟刷出：

```
[2026-09-19 03:10:50] 🚨 CRITICAL 可用内存 3400MB < 4000MB ⇒ **暂停启动**（不杀在跑臂）；活跃臂=3 提交可用=3400MB
```

而本项目既有巡检口径（run143~147 连续 5 轮）报 **提交余量 33GB 量级、安全**。**两个数字相差近 10 倍，若不加辨识会直接误判为事故。**

### 根因（源码级确证，`_q5l_launch.py:220-222`）

```python
if mm['avail'] < DANGER_MB:
    log('🚨 CRITICAL 可用内存 %dMB < %dMB ⇒ **暂停启动**（不杀在跑臂）；活跃臂=%d 提交可用=%dMB'
        % (mm['avail'], DANGER_MB, len(act), mm['avail']))
                                                  ^^^^^^^^^^^^^^ 三次实参全为 mm['avail']
```

- 该格式串的第四个占位符写的是「**提交可用**」，但实参传的是 `mm['avail']`（= `GlobalMemoryStatusEx.ullAvailPhys`，**物理可用内存**）。
- **正确的提交余量字段是 `mm['commit_free']`（= `ullAvailPageFile`），在 CRITICAL 分支中从未被读取**。
- 对照：同文件 `:229` 的闸②分支格式串写的是「可用 %dMB(<%d) 或 提交可用 %dMB(<%d)」，对应 `mm['avail'], GATE_MB, mm['commit_free'], COMMIT_FLOOR_MB` ⇒ **闸②的标签是对的**。⇒ **仅 CRITICAL 分支一处标签错误**，属可精确定位的单点缺陷。

### 独立复核（`_p148_mem.py` ×3 / `_p148_mem2.py` ×10）

| 指标 | 读数 | 与启动器日志比对 |
|---|---|---|
| `ullAvailPhys`（物理可用） | 2910MB（复测）／2387~3296MB（十点） | **与日志「3400MB」同量级 ⇒ 确认为同一字段** |
| `ullAvailPageFile`（提交余量） | **30369MB** | 日志 CRITICAL 行的「提交可用」**与之无关** |
| `dwMemoryLoad` | 89~92% | 高负载，与物理可用低一致 |
| `ullTotalPageFile` | 79369MB | 未缩 |

**结论**：启动器日志中的「提交可用=NMB」**不是提交余量**，而是物理可用内存。**R-164 成立。**

### 等级与影响面

- **等级【中】**（不改任何 Sharpe/Calmar/MaxDD/单位敞口结论，不影响 D-174；但**直接威胁运维判据的可读性**）。
- **影响面①（判据污染）**：任何按字面读「提交可用」并套用用户阈值（>10GB 安全 / <8GB 降 1 臂）的人，会得出「提交余量 3.4GB ⇒ 严重危险、需降臂至 1 臂」的**错误结论**。**本轮巡检已按物理量纲正确区分，未误判、未误降臂。**
- **影响面②（历史极值被误读）**：日志历史极值 `855MB`（2026-09-18 04:15:42）、`1099MB`（09-18 14:00）、`1303MB`（09-18 22:30）、`1660MB`（09-19 02:55）—— **全部是物理可用内存**，而非提交余量。物理可用曾 <1500MB 的采样在两启动器合计 **5 次**（全在 q5l 日志）。
- **影响面③（重要澄清）**：物理可用 <1500MB **并不等同于**用户阈值「<8GB ⇒ 降 1 臂」，因为二者量纲不同：用户口径的「提交余量」= `ullAvailPageFile`，当前 **29~30.8GB**，**从未接近 8GB**。⇒ **本轮及此前各轮的降臂阈值均未被触发**，用户既定「提交余量」纪律**如实成立**。

### 处置

## 三、★ 实质发现：启动器门禁倒挂（附带观察）

### 现象

`_q5l_launch.py` 中同时存在两级门禁：

```python
DANGER_MB = 4000           # 低于此值 ⇒ 暂停启动并告警   (line 37)
GATE_MB   = 6000           # ullAvailPhys 门禁（偏乐观读数，故配 cap=3 双保险）  (line 35)
COMMIT_FLOOR_MB = 20000    # 提交余量下限   (line 36)
```

判据链为 `if avail < DANGER_MB` → `elif pend and len(act) >= MAX_ARMS` → `elif pend and (avail < GATE_MB or commit_free < COMMIT_FLOOR_MB)`。

### 分析

- **DANGER_MB(4000) < GATE_MB(6000)** ⇒ 物理可用落在 **[4000, 6000)** 区间时，走的是闸②分支（条件 `avail < GATE_MB` 成立）⇒ 行为一致（等待），**结果无差异**。
- 但**语义**倒挂：`DANGER`（危险）阈值低于 `GATE`（门禁）阈值，命名与实际严重度序相反。物理可用 5000MB 时既「未达危险」又「被门禁挡住」，日志措辞会让人误以为只是常规等待。
- **实测当前状态**：物理可用 2387~3296MB < 4000MB ⇒ **长期落在 CRITICAL 分支**。两启动器的近 40 分钟日志中，**CRITICAL 连续刷屏**（q5l 02:55~03:10 连续 6 次、q5c 02:54~03:04 连续 4 次），而「等待中：活跃臂=3 可用=5129MB」类常规行仅在 02:20 / 02:50 出现。
- **等级【低】**（不影响任何实验结论，且因 `cap=3` 双保险 + 3 臂已满额，**实际未产生任何起臂行为差异**）。
- **处置**：并入合并改造清单，建议重命名/重定序为 `GATE_MB(6000) > WARN_MB(4000)`，或直接合并为单级。

### 风险评级说明（重要）

物理可用内存长期处于 **2.4~3.3GB（load 89~92%）**，**无 MemoryError / OutOfMemory / WinError 1455 / 页面文件告警**（全日志 grep 为空）⇒ **当前无功能性风险**。
但该状态意味着**系统已高度依赖页面文件换入换出**；若此时再起第 4 臂或遭遇大内存峰值，**触发 1455（页面文件不足）的概率实质性上升**。⇒ **本轮维持不起臂、不重启、严格 3 臂封顶**，与用户「<8GB ⇒ 只降不升」纪律方向一致。
